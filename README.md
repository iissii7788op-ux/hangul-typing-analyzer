# 오타지도 (한글 타자 오류 패턴 분석 및 맞춤 연습 문장 생성 서비스)

정보과학 프로젝트 · 2510 이정현

**배포 주소: https://hangul-typing-analyzer.vercel.app**

## 무엇을 만드나

기존 타자 연습 사이트는 **분당 타수와 정확도 퍼센트만** 알려 준다.
내가 *어떤 글자에서 왜* 틀리는지는 알려 주지 않아서, 틀리는 부분만 골라 연습할 방법이 없다.

이 서비스는 제시 문장을 따라 타이핑하면 **자모 단위로** 어떤 글자를 어떤 글자로 잘못 쳤는지
분석해서, 자판 히트맵 · 취약 자모 순위표를 보여 주고, 그 자모가 집중된 **맞춤 연습 문장**을
자동으로 만들어 준다.

## 기능 범위 (1차시 확정)

### 1단계 — 프론트엔드만으로 동작 (2~5차시)
- [x] 제시 문장 / 타이핑 입력창 / 완료 버튼 화면, 결과·기록 화면 배치

- [x] 오타 유형 분류: 교체 / 삽입 / 삭제 / 자리바꿈
- [x] 교체일 때 두벌식 자판 좌표로 키 사이 거리 계산 → 옆 키 오타 vs 먼 키 오타
- [x] 자모별 평균 입력 시간 → 틀리진 않지만 느린 자모 찾기

- [x] Vercel 배포

### 2단계 — Supabase 연결 (6~8차시)
- [x] 연습 기록 저장 (제시 문장, 입력 문장, 시간, 정확도, 날짜)
- [x] 사용자별 자모 오류 쌍 / 평균 입력 시간 **누적** 집계

## 화면 구성

계획서 3번 스케치대로 화면 3개를 만들었다. html 파일을 3개로 나누지 않고
한 페이지에 두고 `hidden` 속성으로 전환한다. 페이지가 넘어가면 연습 중에 모은
데이터(입력 문장, 키 입력 시각)가 전부 사라지기 때문이다.

| 화면 | 구성 |
|---|---|
| 연습 | 모드 선택 · 제시 문장 · 입력창 · 경과 시간/진행 · 완료 |
| 결과 | 요약줄 · 2×2(자판 히트맵 · 느린 자모 · 오답 순위 · 오타 유형) · 맞춤 연습 문장 |
| 기록 | 회차별 정확도 그래프 · 누적 취약 자모 · 연습 기록 |

결과 화면에서 '입력이 느린 자모' 칸은 채워졌다. 나머지 칸(자판 히트맵, 자모 오답 순위,
오타 유형, 맞춤 연습 문장)은 편집 거리가 필요해 4~5차시에 채운다. 자리마다 몇 차시인지 적어 두었다.

기록 화면은 스케치대로 안쪽 구조까지 만들었다. 꺾은선 그래프는 라이브러리 없이
SVG 를 직접 만들고, 취약 자모와 연습 기록은 목록으로 그린다. 실제 기록은 7~8차시에
Supabase 에서 불러오므로, 지금은 `SAMPLE_RECORD` 예시 데이터로 호출해 배치를 확인한다.
그리는 함수와 데이터를 나눠 두어서 나중에 데이터만 바꿔 끼우면 된다.
예시라는 것은 화면에 배지로 표시해 두었다.

### 제시 문장을 글자마다 span 으로 쪼개는 이유

```
"안녕하세요" → <span>안</span><span>녕</span><span>하</span><span>세</span><span>요</span>
                  [0]        [1]        [2]        [3]        [4]
```

문장을 통째로 넣으면 3차시에 틀린 글자만 색칠할 수 없다. 글자 하나하나가
따로 손댈 수 있는 요소여야 한다. 이 span 의 순서는 `decomposeToKeysDetailed` 가
붙여 주는 `charIndex` 와 그대로 짝이 맞는다. 4차시에 편집 거리로 틀린 키를
찾으면 `charIndex` 로 몇 번째 글자인지 알아내 그 span 을 색칠하게 된다.

## 자모 분해 원리 메모

한글 완성자(가~힣)는 유니코드에 규칙적으로 배열되어 있다.

```
코드 = 0xAC00 + (초성번호 × 21 + 중성번호) × 28 + 종성번호
```

초성 19개 · 중성 21개 · 종성 28개(받침 없음 = 0번)이므로,
한 초성이 차지하는 칸은 21 × 28 = 588칸.

이 식을 거꾸로 풀면 사전 없이 나눗셈만으로 분해된다.

```
offset  = 코드 - 0xAC00
종성번호 = offset % 28
중성번호 = (offset / 28) % 21
초성번호 = (offset / 28) / 21
```

검산 — `안`(0xC548) → offset 6472
→ `6472 % 28 = 4`(ㄴ), `6472/28 = 231`, `231 % 21 = 0`(ㅏ), `231/21 = 11`(ㅇ) → ㅇ,ㅏ,ㄴ ✅

### 두 단계 분해 — 왜 둘 다 필요한가

유니코드가 세는 단위와 손가락이 누르는 단위는 다르다.
유니코드는 `ㅄ`을 완성된 종성 하나로 보지만, 두벌식 자판에 `ㅄ` 키는 없다.

```
"값" ──decompose──> [ㄱ, ㅏ, ㅄ] ──toKeys──> [ㄱ, ㅏ, ㅂ, ㅅ]
        (자모 단위)                          (키 단위)
```

`값`을 `갑`으로 잘못 쳤을 때 두 방식의 결론이 갈린다.

| 단위 | 비교 | 결론 |
|---|---|---|
| 자모 | `ㄱㅏㅄ` vs `ㄱㅏㅂ` | ㅄ을 ㅂ으로 **교체**했다 (자판에 없는 오타) |
| 키 | `ㄱㅏㅂㅅ` vs `ㄱㅏㅂ` | ㅅ을 **빼먹었다**(삭제) — 실제로 손가락이 한 일 |

그래서 4차시 편집 거리(DP)와 자판 거리 계산은 **키 단위**를 기준으로 한다.
반면 결과 화면의 자모 오답 순위표는 사람이 읽는 것이라 **자모 단위**가 자연스럽다.
두 함수를 모두 남겨 둔 이유다.

쪼개는 대상은 겹받침 11개(ㄳ ㄵ ㄶ ㄺ ㄻ ㄼ ㄽ ㄾ ㄿ ㅀ ㅄ)와
복합 모음 7개(ㅘ ㅙ ㅚ ㅝ ㅞ ㅟ ㅢ)뿐이다.

**쪼개면 안 되는 것**
- `ㅐ ㅔ ㅒ ㅖ` — 모양은 ㅏ+ㅣ 처럼 생겼지만 두벌식에서는 각각 독립된 키(o, p, Shift+o, Shift+p)
- `ㄲ ㄸ ㅃ ㅆ ㅉ` — Shift 조합이지만 누르는 키는 하나
- 그래서 `ㅙ`를 ㅗ+ㅐ로 쪼갠 뒤 **거기서 멈춰야** 한다. 재귀로 계속 쪼개면 ㅐ까지 분해되어 틀린다.

### 받침이 없을 때 종성 자리를 비울 것인가 (설계 결정 기록)

받침이 없으면 종성을 아예 넣지 않아 글자마다 칸 수가 달라진다(`가`=2칸, `값`=3칸).
대안으로 종성 자리를 빈칸으로 채워 항상 3칸 고정으로 만드는 방법을 검토하고,
편집 거리를 실제로 돌려 비교했다.

| 상황 | 현재 방식 (받침 없으면 생략) | 대안 (항상 3칸 고정) |
|---|---|---|
| `가` → `갈` | **삽입** ㄹ | 교체 (빈칸)→ㄹ |
| `안녕` → `아녕` | **삭제** ㄴ | 교체 ㄴ→(빈칸) |
| `나무` → `남무` | **삽입** ㅁ | 교체 (빈칸)→ㅁ |

편집 **거리**는 양쪽 다 1로 같지만 **오타 유형**이 갈린다.
고정 길이 방식은 받침 관련 오타를 전부 "교체"로 만들어, 오타 유형 분류 기능을 무의미하게 한다.
실제로 손가락이 한 일은 ㄹ 키를 한 번 **더 누른 것**(삽입)이지 빈칸 키를 바꿔 누른 것이 아니다.

추가로 고정 길이 방식은
- `(빈칸)→ㄹ` 오타의 자판 좌표가 없어 키 사이 거리를 계산할 수 없고,
- 히트맵에 칠할 자리가 없으며,
- 자모 통계마다 빈 문자열을 걸러내야 하고,
- 키 단위 분해에서는 글자당 칸 수가 2~4개로 달라져 **애초에 성립하지 않는다**.

**결론: 현재 방식 유지.** 다만 고정 길이가 노렸던 장점(글자 번호를 `index / 3`으로 계산)은
실제로 필요하므로, 길이를 고정하는 대신 **꼬리표**로 해결했다.

```js
decomposeToKeysDetailed('값')
// [{ key:'ㄱ', charIndex:0, role:'cho',  fromComplex:false },
//  { key:'ㅏ', charIndex:0, role:'jung', fromComplex:false },
//  { key:'ㅂ', charIndex:0, role:'jong', fromComplex:true  },
//  { key:'ㅅ', charIndex:0, role:'jong', fromComplex:true  }]
```

`charIndex`로 3차시의 틀린 글자 색칠이 가능하고, `role`로 초성/중성/종성별 오류 경향까지 낼 수 있다.

## 한글은 글자가 완성되기 전을 지나간다 (3차시)

`안` 을 치면 화면에 ㅇ -> 아 -> 안 순서로 나타난다. 영어는 `a` 를 누르면 곧바로 `a` 지만
한글은 조합 중인 중간 상태를 거친다. 제시 글자와 다르면 무조건 빨갛게 칠하면,
정확히 치고 있는데도 빨강 -> 빨강 -> 초록으로 깜빡여서 쓰기 괴로운 화면이 된다.

그래서 판정을 네 가지로 나눈다.

| 상태 | 언제 | 표시 |
|---|---|---|
| `correct` | 제시 글자와 같다 | 파란색 |
| `typing` | 아직 완성 전인데 제시 글자로 **가는 길 위**에 있다 | 파란색 + 밑줄 |
| `wrong` | 그 길에서 벗어났다 | 빨간 배경 |
| `pending` | 아직 치지 않았다 | 기본색 |

"길 위에 있는지"는 1차시에 만든 `decomposeToKeys` 로 판단한다.

```
제시 "값"  -> ㄱㅏㅂㅅ
친 것 "갑" -> ㄱㅏㅂ     앞부분이므로 typing  (겹받침도 중간을 지나간다)
친 것 "간" -> ㄱㅏㄴ     앞부분이 아니므로 wrong
```

맞게 친 글자는 처음에 흐린 회색이었다. '지나간 곳' 이라는 뜻이었는데 흰 바탕에서
대비가 약해 친 내용을 되짚어 보기 어려웠다. 한컴 타자처럼 파란색으로 바꾸고,
조합 중인 글자와는 밑줄로 구분한다.

단, **마지막으로 친 글자만** 이렇게 본다. 이미 지나간 글자는 조합이 끝났으므로
엄격하게 비교한다. `안녕` 을 `아녕` 으로 쳤다면 조합 중이 아니라 받침을 빼먹은 것이다.

### 키 입력 시각은 왜 keydown 으로 재지 않나

한글은 IME(입력기)를 거치기 때문에 `keydown` 이벤트의 `key` 값이 실제 자모로 오지 않는다.
그래서 **화면에 실제로 나타난 자모**를 기준으로 삼는다. 입력이 바뀔 때마다 키 배열로
쪼개서 늘어난 만큼 지금 시각을 붙이고, 백스페이스로 지우면 기록도 같이 잘라낸다.

시각은 `Date.now()` 가 아니라 `performance.now()` 로 잰다. 더 촘촘하고(소수점 이하 ms),
도중에 시스템 시계가 바뀌어도 영향을 받지 않는다.

자모별 평균을 낼 때 **공백과 문장부호는 뺀다.** 스페이스바도 분명 키 입력이지만 자모가
아니라서, 섞어 두면 '입력이 느린 자모' 순위에 공백이 1등으로 올라온다.

### 판정을 화면과 분리한 이유

`typing.js` 는 DOM 을 건드리지 않고 값만 다룬다. 조합 중 상태는 브라우저에서 손으로
쳐 가며 확인하기 어렵다. 값만 다루는 함수로 떼어 두면 `안` 을 치는 도중의 `ㅇ`, `아` 같은
상태를 테스트로 직접 넣어 볼 수 있다.

## 기록을 보고 와도 치던 내용이 남아 있어야 한다

연습 도중 '기록 보기' 로 나갔다 돌아오면 치던 내용이 경고 없이 사라졌다.
기록 화면의 '연습하기' 와 결과 화면의 '다시 하기' 가 같은 버튼 취급을 받아
둘 다 새 연습을 시작했기 때문이다. 두 버튼은 사용자의 뜻이 다르다.

| 버튼 | 사용자의 뜻 | 하는 일 |
|---|---|---|
| 기록 → 연습하기 | 잠깐 보고 돌아왔다 | 문장과 입력을 그대로 두고 이어서 |
| 결과 → 다시 하기 | 연습을 끝내고 새로 | 새 문장을 뽑는다 |

이어서 칠 수 있게 하니 확인 창이 필요 없어졌다. 다만 시간을 재는 방식 두 가지를
같이 고쳐야 했다.

### 연습 시간은 '재고 있는 구간들의 합' 으로 센다

시작 시각 하나만 두고 `지금 - 시작` 으로 빼면, 기록 화면에 1분 머문 시간까지
연습 시간에 들어간다. 그래서 멈출 때마다 그때까지 잰 만큼을 합에 더하고 구간을 닫는다.

```js
function currentElapsed() {
  return elapsedMs + (startedAt === null ? 0 : performance.now() - startedAt);
}
```

### 키 입력 시각도 벽시계가 아니라 경과 시간으로 잰다

처음에는 '돌아올 때 마지막 키의 시각을 지금으로 당기는' 보정 함수를 만들었다.
그런데 테스트가 바로 잡아냈다. 마지막 키의 시각을 바꾸면 **이미 확정된 그 키의
입력 시간까지 오염된다.** 150ms 였던 값이 30150ms 가 되어 버렸다.

보정하는 대신 기준 자체를 바꿨다. 키 입력 시각으로 벽시계 시각이 아니라
위에서 만든 `currentElapsed()` 를 넘긴다. 화면을 떠나 있는 동안은 시계가 멈춰
있으므로 그 시간이 애초에 더해지지 않고, 따로 보정할 일이 없어진다.

## 편집 거리 — 왜 완전탐색이 아니라 DP인가 (4차시)

제시 문장은 키 단위로 40개쯤 된다. 완전탐색이라면 자리마다
'교체할까, 빠뜨린 걸로 볼까, 더 친 걸로 볼까' 를 전부 시도해야 하니
갈래가 자리마다 3개씩 생겨 **3⁴⁰ ≈ 1경 2천조 가지**가 된다. 끝나지 않는다.

DP 는 "제시 앞 i개를 입력 앞 j개로 바꾸는 최소 편집 횟수" 를 표 한 칸에 **한 번만**
적어 두고 계속 다시 쓴다. 칸은 `41 × 41 = 1681개` 뿐이다. 같은 계산을 반복하지
않는 것이 전부다.

### 거리만으로는 부족하다 — 역추적

편집 거리는 '최소 몇 번' 이라는 숫자만 준다. 우리에게 필요한 건
'어느 자모를 어느 자모로 잘못 쳤는가' 다. 그래서 표를 다 채운 뒤
오른쪽 아래에서 왼쪽 위로 거꾸로 되짚으며 연산 하나하나를 복원한다.

### 같은 횟수를 주는 길이 여럿일 때 (계획서 5번에 적은 걱정)

`ㅕㄱㅏㅅ` 을 `ㅛㅏㅅ` 으로 쳤다면 두 가지로 설명되고 **둘 다 2번**이다.

| | 설명 | 그럴듯한가 |
|---|---|---|
| A | ㅕ 를 ㅛ 로 잘못 치고(옆 키) ㄱ 을 빠뜨렸다 | 그럴듯하다 |
| B | ㅕ 를 빠뜨리고 ㄱ 을 ㅛ 로 잘못 쳤다(먼 키) | 어색하다 |

처음에는 '교체를 먼저 집는다' 는 규칙만 뒀는데, 역추적이 뒤에서 앞으로 가다 보니
**B** 를 골랐다. 테스트가 이를 잡아냈다.

타자에서는 옆 키를 잘못 누르는 실수가 압도적으로 흔하고 멀리 떨어진 키를 누르는
일은 드물다. 그래서 순서를 이렇게 정했다.

1. 자리바꿈 — 두 자모를 한 번으로 묶으므로 가장 먼저
2. **옆 키 교체** — 가장 흔한 실수라 바로 인정
3. 빠뜨림 / 덧침
4. 먼 키 교체 — 다른 설명이 없을 때만

### 오타 유형 다섯 가지

| 편집 연산 | 화면 표시 | 가르는 기준 |
|---|---|---|
| 교체 | 옆 키 오타 / 원거리 오타 | 두벌식 자판 좌표상 거리 ≤ 1.5 |
| 삭제 | 빠뜨림 | |
| 삽입 | 덧침 | |
| 자리바꿈 | 자리바꿈 | |

자판은 줄마다 조금씩 오른쪽으로 밀려 있어서(`ROW_OFFSET`) 그 어긋남을 반영해야
대각선 이웃까지 제대로 '옆 키' 로 잡힌다.

## 한 라운드에 문장 다섯 개

처음에는 문장 하나를 치면 바로 결과가 나왔다. 그런데 한 문장에서 나오는 자모는
40개 남짓이라 취약 자모를 가릴 만큼 표본이 모이지 않는다. 한컴 타자처럼
**엔터를 누르면 다음 문장**으로 넘어가고, 다섯 문장을 모두 치면 결과가 나온다.

- 엔터로 접은 문장만 집계한다. 치다 만 문장을 넣으면 아직 치지 않은 뒷부분이
  전부 '빠뜨림' 으로 쌓인다. (손도 안 댄 문장 하나 때문에 빠뜨림 39회가 잡힌 적이 있다.)
- 시계는 문장이 바뀌어도 계속 간다. 분당 타수는 라운드 전체 기준이다.
- 자모 입력 시간은 문장마다 새로 잰다. 문장 사이의 빈 시간이 섞이지 않게 하려는 것이다.
- 조합 중에 누른 엔터(`e.isComposing`)는 글자를 확정하는 용도라 넘기지 않는다.

## 고쳐서 흔적이 지워진 오타도 센다 (두 번 고친 부분)

오타를 내면 보통 백스페이스로 지우고 다시 친다. 그러면 최종 입력에는 흔적이
남지 않아 '오타 0곳' 이 되어 버린다.

```
ㅇㅏㄴㄴ[ㅛ]   오타를 냄
ㅇㅏㄴㄴ       지움
ㅇㅏㄴㄴㅕㅇ   고쳐서 완성   ->  최종 입력은 정답
```

하지만 ㅕ 를 ㅛ 로 잘못 친 것은 사실이고, 타자 연습에서는 그게 바로 알아야 할 정보다.

### 첫 시도 — 지우는 순간을 잡는다 (실패)

처음에는 입력이 **줄어드는 순간**에 지워지기 직전 상태를 맞춰 보고 오타를 건졌다.
잘 되는 듯했지만 **줄어들지 않으면서 고쳐지는 길**이 여럿 있었다.

| 고치는 방법 | 키 개수 | 건져지나 |
|---|---|---|
| 백스페이스로 지우고 다시 | 6 → 5 | 잡힘 |
| 글자를 골라 덮어쓰기 | 6 → 6 | **놓침** |
| 조합이 이어지며 고쳐짐 (`값ㅆ` → `값싸`) | 5 → 6 | **놓침** |
| 오타 글자에 받침이 붙음 | 6 → 7 | **놓침** |

한글은 조합 중에 글자가 통째로 바뀌기도 해서 **'줄어듦' 이라는 신호 자체를 믿을 수 없다.**

### 두 번째 — 치는 내내 기록한다

지우는 순간을 노리는 대신, **칠 때마다 맞춰 보고 본 적 없는 오타면 적어 둔다**(`trackErrors`).
한 번이라도 틀렸으면 기록이 남으므로 그 뒤에 어떻게 고치든 상관없다.

기록의 열쇠는 '제시 문장의 몇 번째 자리에서 무엇을 무엇으로' 다. 같은 자리에서 같은
실수를 되풀이해도 한 번으로 센다. 백스페이스를 눌렀다 다시 치는 동안 같은 오타가
여러 번 보이는 것을 막으려는 것이다.

빠뜨림(`DELETE`)은 이때 적지 않는다. 치는 도중에는 아직 안 친 뒷부분이 전부 빠뜨림으로
보이기 때문이다. 그것은 문장을 다 치고 나서 따로 센다(`missingErrors`).

**맞게 치는 동안에는 오탐이 생기지 않는다.** 한글은 조합 과정이 늘 제시 문장의
앞부분이 되기 때문이다(`ㄱ → 가 → 갑 → 값`). 1차시에 키 단위로 쪼개 둔 것이 여기서도 받쳐 준다.

## 배포 (Vercel)

빌드 과정이 없는 정적 사이트라서 파일을 그대로 올린다.
GitHub 저장소를 연결해 두면 `git push` 할 때마다 자동으로 다시 배포된다.

`vercel.json` 은 캐시 설정 하나만 담고 있다.

```
Cache-Control: public, max-age=0, must-revalidate
```

"저장해 두되 쓰기 전에 매번 바뀌었는지 확인하라" 는 뜻이다. 개발 중에 파일을 고쳐도
브라우저가 옛날 css/js 를 붙들고 있어 화면이 그대로인 문제를 겪었는데, 배포한 곳에서도
같은 일이 생기면 고친 내용이 방문자에게 안 간다.

## 자판 히트맵 (5차시)

4차시에 만든 자판 좌표를 그대로 그림으로 옮긴다. 자판 모양 그대로 보여 줘야
'오른손 가운데 줄에서 실수가 몰린다' 같은 것이 한눈에 들어온다.

많이 틀린 키일수록 진하게 칠한다. 가장 많이 틀린 키를 1 로 두고 비율만큼
`fill-opacity` 를 준다. Shift 로 치는 자모(ㄲ, ㅆ…)는 같은 키이므로 기본 자모와
횟수를 합쳐 센다.

세는 기준은 **쳤어야 할 자모**(`from`)다. 'ㅕ 를 칠 자리에서 자꾸 실수한다' 가
연습에 쓸모 있는 정보이기 때문이다. 덧침만은 쳐야 할 자모가 없으므로 실제로
누른 키로 센다.

## 맞춤 연습 문장 — 배낭 알고리즘 (5차시)

### 취약 자모 고르기

오타가 난 자모와 '틀리지는 않았지만 유독 오래 걸린' 자모를 함께 본다.
손이 익지 않은 자리는 둘 중 하나로 드러나기 때문이다.
오류가 더 뚜렷한 신호라서 오타 한 번에 10점, 입력 시간은 50ms 당 1점을 준다.
오타 한 번이 느림 500ms 와 맞먹는 셈이다.

### 배낭 문제로 보기

| 배낭 문제 | 우리 문제 |
|---|---|
| 담을 수 있는 무게 | 글자 수 제한 (20자) |
| 물건의 무게 | 단어의 글자 수 |
| 물건의 가치 | 그 단어에 든 취약 자모 개수 |

같은 단어를 여러 번 담을 수 있게 하면 한 단어만 반복되는 문장이 나온다
(계획서 5번에서 걱정한 그대로다). 그래서 단어마다 한 번씩만 쓰는 **0/1 배낭**으로 푼다.

여기서도 DP 를 쓰는 이유는 편집 거리와 같다. 단어를 넣을지 말지 전부 따지면
160개 단어에 **2¹⁶⁰ 가지**가 되지만, 표는 `단어 수 × 글자 수` 칸이면 된다.
표를 채운 뒤 거꾸로 되짚어 실제로 넣은 단어를 복원하는 것도 편집 거리와 같다.

예) 취약 자모가 ㄹ ㅏ ㄴ 일 때
```
칠판 빨래 신발 하늘 바람 산길 눈물 사랑 닭 삶 날짜
```

## 데이터베이스 (6~8차시)

Supabase(PostgreSQL)에 표 세 개를 두었다. 설계는 `supabase/schema.sql` 에 있다.

| 표 | 담는 것 |
|---|---|
| `practice_sessions` | 라운드 요약 — 정확도, 분당 타수, 오타 수, 걸린 시간, 문장들, 맞춤 문장 |
| `session_errors` | 그 라운드에서 나온 오류 쌍 (쳤어야 할 자모, 실제로 친 자모, 유형, 횟수) |
| `session_jamo_times` | 그 라운드의 자모별 평균 입력 시간 |

문장은 라운드마다 여러 개지만 문장 하나하나를 따로 뒤질 일이 없어서
`practice_sessions` 안에 `[{target, typed}]` 꼴로 함께 담았다.

### 로그인을 시키지 않고 사용자를 가리는 법

회원가입을 받으면 타자 한 번 쳐 보려는 사람이 떠난다. 그래서 **익명 로그인**을 쓴다.
계정은 없지만 사용자마다 고유한 id 가 생기고, 그 id 로 '내 기록' 을 가릴 수 있다.
로그인 상태는 브라우저에 남아서 다시 들어와도 같은 사람으로 이어진다.

### 공개 키는 숨길 수 없다 — 그래서 RLS

브라우저에서 데이터베이스를 부르려면 키가 필요한데, 그 키는 페이지에 그대로 실려 나간다.
개발자 도구만 열면 누구나 볼 수 있으니 **숨기는 것이 애초에 불가능**하다.

그래서 키를 감추는 대신 **RLS(Row Level Security)** 로 막는다.
표마다 "`auth.uid()` 와 `user_id` 가 같은 줄만 읽고 쓸 수 있다" 는 규칙을 걸어 두면,
키를 가져가도 남의 기록은 건드릴 수 없다.

```sql
create policy "자기 연습 기록만" on practice_sessions
  for all using (auth.uid() = user_id) with check (auth.uid() = user_id);
```

### 누적 합계를 따로 저장하지 않은 이유

계획서에는 누적 집계를 저장한다고 적었지만, 실제로는 회차별 기록만 담고
**불러올 때 더한다.** 합계를 따로 저장하면 연습을 저장할 때와 합계를 고칠 때가
어긋나는 순간 숫자가 틀어지고, 한번 틀어지면 되돌리기 어렵다.
기록이 몇 백 줄 수준이라 그때그때 더하는 편이 단순하고 틀릴 일이 없다.

### 저장이 실패해도 결과는 보여 준다

저장은 네트워크를 타는 일이라 실패할 수 있다. 실패했다고 결과 화면을 막으면
연습한 내용을 아예 못 보게 된다. 그래서 결과를 먼저 띄우고 저장은 뒤에서 돌리며,
어떻게 됐는지만 작은 글씨로 알려 준다.

## 한/영 전환을 안 하고 쳤을 때

누적 취약 자모에 알파벳이 섞여 나오는 문제가 있었다.
`교실` 을 영문 상태로 치면 `ryslf` 가 들어와 `ㄱ→r`, `ㅛ→y` 같은 오류 쌍이 잡힌다.

**이것은 자판 실수가 아니다.** 손가락은 ㄱ 자리(R키)를 정확히 눌렀고,
한글 모드가 아니었을 뿐이다. 그런데 자모 통계에 섞이면

- 자모 오답 순위에 알파벳이 오르고
- 알파벳은 자판 좌표가 없어 오타 유형이 전부 '원거리 오타' 가 되고
- 멀쩡한 키가 히트맵에 빨갛게 칠해지고
- **엉뚱한 자모가 취약 자모로 뽑혀 쓸모없는 맞춤 문장이 만들어진다**

고치면서 두 겹으로 막았다.

**첫째, 자모가 아닌 오류는 자모 통계에서 뺀다**(`isJamoError`).
틀린 것은 맞으므로 오타 개수와 정확도에는 그대로 남긴다.

**둘째, 그런 문장은 통째로 집계에서 뺀다.** 자모 하나하나만 걸러서는 모자랐다.
영문으로 치면 제시 문장과 아예 어긋나서, 치지도 않은 뒷부분이 전부 '빠뜨림' 으로
쌓이고 그 자모들이 취약 자모로 뽑혔기 때문이다.

| | 고치기 전 | 고친 후 |
|---|---|---|
| 정확도 | 3% | 95% |
| 오타 | 38곳 | 2곳 |
| 히트맵 | 12개 키 | 2개 |
| 취약 자모 | ㅅ ㄱ ㅛ (엉뚱) | ㄹ ㅏ ㄷ (실제 오타) |

**셋째, 치는 중에 알려 준다.** 통계에서 걸러 내기만 하면 '왜 오타가 안 잡히지?' 하고
더 헷갈린다. 한글 아닌 글자가 세 개를 넘으면 입력창 아래에 한/영 키를 확인하라고 띄운다.

## 한글 조합 중 엔터가 삼켜지던 문제

문장을 다 치고 바로 엔터를 누르면 넘어가지 않았다. 한글은 마지막 글자가 '조합 중'
인 상태가 있고, 그때 누른 엔터는 **글자를 확정하는 데 쓰인다**(`e.isComposing`).
사용자 눈에는 '엔터를 눌렀는데 가만히 있는' 것으로 보인다.

여기에 '엔터로 접은 문장만 집계한다' 는 규칙이 맞물려 더 나빠졌다.
엔터가 먹히지 않자 '그만하고 결과 보기' 를 누르게 되고, 그 문장은 집계되지 않아
**오타가 하나도 안 뜨는** 일이 생겼다.

- 엔터를 눌렀다는 사실을 적어 두었다가 조합이 끝나는 순간 이어서 처리한다
- '그만하고 결과 보기' 도 치던 문장을 **친 만큼** 담는다
  (제시 문장을 입력 길이에 맞춰 잘라서 견준다. 안 친 뒷부분까지 넣으면 빠뜨림만 쌓인다)

## 같은 오타가 여러 번 세어지던 문제

치는 내내 오타를 기록하게 바꾸고 나서, 오타 하나가 여럿으로 불어나는 일이 생겼다.

```
"희망찬 목소리루"     -> ㅓ>ㅜ 로 기록
"희망찬 목소리루 "    -> ㅡ>ㅜ 로 기록   (같은 오타인데 다르게 잡힘)
"희망찬 목소리루 인"  -> ㅗ>ㅜ 로 기록   (이게 맞는 것)
```

입력이 아직 제시보다 짧으면 **뒤쪽이 통째로 빠뜨림**이 되고, 그 틈에서 `ㅜ` 를
제시의 어느 자모와 맞출지가 글자를 칠 때마다 바뀐다. 자리가 달라지니 기록의 열쇠도
달라져 중복 거르기가 소용없었다.

제시 문장을 **지금까지 친 만큼 잘라서** 견주니 해결됐다. 뒷부분이 사라져 정렬이
흔들리지 않는다.
