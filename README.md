# 오타지도 (한글 타자 오류 패턴 분석 및 맞춤 연습 문장 생성 서비스)

정보과학 프로젝트 · 2510 이정현

## 무엇을 만드나

기존 타자 연습 사이트는 **분당 타수와 정확도 퍼센트만** 알려 준다.
내가 *어떤 글자에서 왜* 틀리는지는 알려 주지 않아서, 틀리는 부분만 골라 연습할 방법이 없다.

이 서비스는 제시 문장을 따라 타이핑하면 **자모 단위로** 어떤 글자를 어떤 글자로 잘못 쳤는지
분석해서, 자판 히트맵 · 취약 자모 순위표를 보여 주고, 그 자모가 집중된 **맞춤 연습 문장**을
자동으로 만들어 준다.

## 기능 범위 (1차시 확정)

### 1단계 — 프론트엔드만으로 동작 (2~5차시)
- [x] 제시 문장 / 타이핑 입력창 / 완료 버튼 화면, 결과·기록 화면 배치
- [x] 입력 중 실시간 오답 색 표시, 글자별 키 입력 시각 기록
- [ ] 자모 단위 편집 거리(DP) + 역추적 → **오류 쌍** 추출 (예: ㅕ → ㅛ)
- [ ] 오타 유형 분류: 교체 / 삽입 / 삭제 / 자리바꿈
- [ ] 교체일 때 두벌식 자판 좌표로 키 사이 거리 계산 → 옆 키 오타 vs 먼 키 오타
- [ ] 자모별 평균 입력 시간 → 틀리진 않지만 느린 자모 찾기
- [ ] 배낭 알고리즘으로 취약 자모가 집중된 맞춤 연습 문장 생성
- [ ] Vercel 배포

### 2단계 — Supabase 연결 (6~8차시)
- [ ] 연습 기록 저장 (제시 문장, 입력 문장, 시간, 정확도, 날짜)
- [ ] 사용자별 자모 오류 쌍 / 평균 입력 시간 **누적** 집계
- [ ] 회차별 정확도 추이 그래프, 누적 취약 자모 기록 화면

### 이번 프로젝트에서 하지 않는 것
- 맞춤법 검사 (오타 원인 분석이 목적이지 교정이 목적이 아님)
- 세벌식 등 두벌식 외 자판
- 실시간 멀티플레이 대결

## 화면 구성

계획서 3번 스케치대로 화면 3개를 만들었다. html 파일을 3개로 나누지 않고
한 페이지에 두고 `hidden` 속성으로 전환한다. 페이지가 넘어가면 연습 중에 모은
데이터(입력 문장, 키 입력 시각)가 전부 사라지기 때문이다.

| 화면 | 구성 |
|---|---|
| 연습 | 모드 선택 · 제시 문장 · 입력창 · 경과 시간/진행 · 완료 |
| 결과 | 요약줄 · 2×2(자판 히트맵 · 느린 자모 · 오답 순위 · 오타 유형) · 맞춤 연습 문장 |
| 기록 | 회차별 정확도 그래프 · 누적 취약 자모 · 연습 기록 |

결과 화면에서 '입력이 느린 자모' 칸은 채워졌다. 나머지 칸(자판 히트맵, 자모 오답 순위,
오타 유형, 맞춤 연습 문장)은 편집 거리가 필요해 4~5차시에 채운다. 자리마다 몇 차시인지 적어 두었다.

기록 화면은 스케치대로 안쪽 구조까지 만들었다. 꺾은선 그래프는 라이브러리 없이
SVG 를 직접 만들고, 취약 자모와 연습 기록은 목록으로 그린다. 실제 기록은 7~8차시에
Supabase 에서 불러오므로, 지금은 `SAMPLE_RECORD` 예시 데이터로 호출해 배치를 확인한다.
그리는 함수와 데이터를 나눠 두어서 나중에 데이터만 바꿔 끼우면 된다.
예시라는 것은 화면에 배지로 표시해 두었다.

### 제시 문장을 글자마다 span 으로 쪼개는 이유

```
"안녕하세요" → <span>안</span><span>녕</span><span>하</span><span>세</span><span>요</span>
                  [0]        [1]        [2]        [3]        [4]
```

문장을 통째로 넣으면 3차시에 틀린 글자만 색칠할 수 없다. 글자 하나하나가
따로 손댈 수 있는 요소여야 한다. 이 span 의 순서는 `decomposeToKeysDetailed` 가
붙여 주는 `charIndex` 와 그대로 짝이 맞는다. 4차시에 편집 거리로 틀린 키를
찾으면 `charIndex` 로 몇 번째 글자인지 알아내 그 span 을 색칠하게 된다.

## 실행 방법

화면을 보려면 로컬 서버가 필요하다. ES 모듈은 `file://` 에서 브라우저가 막는다.

```bash
python dev-server.py
```

`python -m http.server` 를 쓰면 파일을 고쳐도 화면이 그대로인 일이 생긴다.
캐시 관련 헤더를 보내지 않아 브라우저가 css/js 를 저장해 두기 때문이다.
`dev-server.py` 는 같은 기능에 "저장하지 말고 매번 새로 받아라" 헤더만 붙인 것이다.

그리고 http://localhost:8000 접속. 자모 분해 테스트는 아래로 실행한다.

```bash
node src/hangul.test.js
node src/typing.test.js
```

## 자모 분해 원리 메모

한글 완성자(가~힣)는 유니코드에 규칙적으로 배열되어 있다.

```
코드 = 0xAC00 + (초성번호 × 21 + 중성번호) × 28 + 종성번호
```

초성 19개 · 중성 21개 · 종성 28개(받침 없음 = 0번)이므로,
한 초성이 차지하는 칸은 21 × 28 = 588칸.

이 식을 거꾸로 풀면 사전 없이 나눗셈만으로 분해된다.

```
offset  = 코드 - 0xAC00
종성번호 = offset % 28
중성번호 = (offset / 28) % 21
초성번호 = (offset / 28) / 21
```

검산 — `안`(0xC548) → offset 6472
→ `6472 % 28 = 4`(ㄴ), `6472/28 = 231`, `231 % 21 = 0`(ㅏ), `231/21 = 11`(ㅇ) → ㅇ,ㅏ,ㄴ ✅

### 두 단계 분해 — 왜 둘 다 필요한가

유니코드가 세는 단위와 손가락이 누르는 단위는 다르다.
유니코드는 `ㅄ`을 완성된 종성 하나로 보지만, 두벌식 자판에 `ㅄ` 키는 없다.

```
"값" ──decompose──> [ㄱ, ㅏ, ㅄ] ──toKeys──> [ㄱ, ㅏ, ㅂ, ㅅ]
        (자모 단위)                          (키 단위)
```

`값`을 `갑`으로 잘못 쳤을 때 두 방식의 결론이 갈린다.

| 단위 | 비교 | 결론 |
|---|---|---|
| 자모 | `ㄱㅏㅄ` vs `ㄱㅏㅂ` | ㅄ을 ㅂ으로 **교체**했다 (자판에 없는 오타) |
| 키 | `ㄱㅏㅂㅅ` vs `ㄱㅏㅂ` | ㅅ을 **빼먹었다**(삭제) — 실제로 손가락이 한 일 |

그래서 4차시 편집 거리(DP)와 자판 거리 계산은 **키 단위**를 기준으로 한다.
반면 결과 화면의 자모 오답 순위표는 사람이 읽는 것이라 **자모 단위**가 자연스럽다.
두 함수를 모두 남겨 둔 이유다.

쪼개는 대상은 겹받침 11개(ㄳ ㄵ ㄶ ㄺ ㄻ ㄼ ㄽ ㄾ ㄿ ㅀ ㅄ)와
복합 모음 7개(ㅘ ㅙ ㅚ ㅝ ㅞ ㅟ ㅢ)뿐이다.

**쪼개면 안 되는 것**
- `ㅐ ㅔ ㅒ ㅖ` — 모양은 ㅏ+ㅣ 처럼 생겼지만 두벌식에서는 각각 독립된 키(o, p, Shift+o, Shift+p)
- `ㄲ ㄸ ㅃ ㅆ ㅉ` — Shift 조합이지만 누르는 키는 하나
- 그래서 `ㅙ`를 ㅗ+ㅐ로 쪼갠 뒤 **거기서 멈춰야** 한다. 재귀로 계속 쪼개면 ㅐ까지 분해되어 틀린다.

### 받침이 없을 때 종성 자리를 비울 것인가 (설계 결정 기록)

받침이 없으면 종성을 아예 넣지 않아 글자마다 칸 수가 달라진다(`가`=2칸, `값`=3칸).
대안으로 종성 자리를 빈칸으로 채워 항상 3칸 고정으로 만드는 방법을 검토하고,
편집 거리를 실제로 돌려 비교했다.

| 상황 | 현재 방식 (받침 없으면 생략) | 대안 (항상 3칸 고정) |
|---|---|---|
| `가` → `갈` | **삽입** ㄹ | 교체 (빈칸)→ㄹ |
| `안녕` → `아녕` | **삭제** ㄴ | 교체 ㄴ→(빈칸) |
| `나무` → `남무` | **삽입** ㅁ | 교체 (빈칸)→ㅁ |

편집 **거리**는 양쪽 다 1로 같지만 **오타 유형**이 갈린다.
고정 길이 방식은 받침 관련 오타를 전부 "교체"로 만들어, 오타 유형 분류 기능을 무의미하게 한다.
실제로 손가락이 한 일은 ㄹ 키를 한 번 **더 누른 것**(삽입)이지 빈칸 키를 바꿔 누른 것이 아니다.

추가로 고정 길이 방식은
- `(빈칸)→ㄹ` 오타의 자판 좌표가 없어 키 사이 거리를 계산할 수 없고,
- 히트맵에 칠할 자리가 없으며,
- 자모 통계마다 빈 문자열을 걸러내야 하고,
- 키 단위 분해에서는 글자당 칸 수가 2~4개로 달라져 **애초에 성립하지 않는다**.

**결론: 현재 방식 유지.** 다만 고정 길이가 노렸던 장점(글자 번호를 `index / 3`으로 계산)은
실제로 필요하므로, 길이를 고정하는 대신 **꼬리표**로 해결했다.

```js
decomposeToKeysDetailed('값')
// [{ key:'ㄱ', charIndex:0, role:'cho',  fromComplex:false },
//  { key:'ㅏ', charIndex:0, role:'jung', fromComplex:false },
//  { key:'ㅂ', charIndex:0, role:'jong', fromComplex:true  },
//  { key:'ㅅ', charIndex:0, role:'jong', fromComplex:true  }]
```

`charIndex`로 3차시의 틀린 글자 색칠이 가능하고, `role`로 초성/중성/종성별 오류 경향까지 낼 수 있다.

## 한글은 글자가 완성되기 전을 지나간다 (3차시)

`안` 을 치면 화면에 ㅇ -> 아 -> 안 순서로 나타난다. 영어는 `a` 를 누르면 곧바로 `a` 지만
한글은 조합 중인 중간 상태를 거친다. 제시 글자와 다르면 무조건 빨갛게 칠하면,
정확히 치고 있는데도 빨강 -> 빨강 -> 초록으로 깜빡여서 쓰기 괴로운 화면이 된다.

그래서 판정을 네 가지로 나눈다.

| 상태 | 언제 | 표시 |
|---|---|---|
| `correct` | 제시 글자와 같다 | 파란색 |
| `typing` | 아직 완성 전인데 제시 글자로 **가는 길 위**에 있다 | 파란색 + 밑줄 |
| `wrong` | 그 길에서 벗어났다 | 빨간 배경 |
| `pending` | 아직 치지 않았다 | 기본색 |

"길 위에 있는지"는 1차시에 만든 `decomposeToKeys` 로 판단한다.

```
제시 "값"  -> ㄱㅏㅂㅅ
친 것 "갑" -> ㄱㅏㅂ     앞부분이므로 typing  (겹받침도 중간을 지나간다)
친 것 "간" -> ㄱㅏㄴ     앞부분이 아니므로 wrong
```

맞게 친 글자는 처음에 흐린 회색이었다. '지나간 곳' 이라는 뜻이었는데 흰 바탕에서
대비가 약해 친 내용을 되짚어 보기 어려웠다. 한컴 타자처럼 파란색으로 바꾸고,
조합 중인 글자와는 밑줄로 구분한다.

단, **마지막으로 친 글자만** 이렇게 본다. 이미 지나간 글자는 조합이 끝났으므로
엄격하게 비교한다. `안녕` 을 `아녕` 으로 쳤다면 조합 중이 아니라 받침을 빼먹은 것이다.

### 키 입력 시각은 왜 keydown 으로 재지 않나

한글은 IME(입력기)를 거치기 때문에 `keydown` 이벤트의 `key` 값이 실제 자모로 오지 않는다.
그래서 **화면에 실제로 나타난 자모**를 기준으로 삼는다. 입력이 바뀔 때마다 키 배열로
쪼개서 늘어난 만큼 지금 시각을 붙이고, 백스페이스로 지우면 기록도 같이 잘라낸다.

시각은 `Date.now()` 가 아니라 `performance.now()` 로 잰다. 더 촘촘하고(소수점 이하 ms),
도중에 시스템 시계가 바뀌어도 영향을 받지 않는다.

자모별 평균을 낼 때 **공백과 문장부호는 뺀다.** 스페이스바도 분명 키 입력이지만 자모가
아니라서, 섞어 두면 '입력이 느린 자모' 순위에 공백이 1등으로 올라온다.

### 판정을 화면과 분리한 이유

`typing.js` 는 DOM 을 건드리지 않고 값만 다룬다. 조합 중 상태는 브라우저에서 손으로
쳐 가며 확인하기 어렵다. 값만 다루는 함수로 떼어 두면 `안` 을 치는 도중의 `ㅇ`, `아` 같은
상태를 테스트로 직접 넣어 볼 수 있다.

## 기록을 보고 와도 치던 내용이 남아 있어야 한다

연습 도중 '기록 보기' 로 나갔다 돌아오면 치던 내용이 경고 없이 사라졌다.
기록 화면의 '연습하기' 와 결과 화면의 '다시 하기' 가 같은 버튼 취급을 받아
둘 다 새 연습을 시작했기 때문이다. 두 버튼은 사용자의 뜻이 다르다.

| 버튼 | 사용자의 뜻 | 하는 일 |
|---|---|---|
| 기록 → 연습하기 | 잠깐 보고 돌아왔다 | 문장과 입력을 그대로 두고 이어서 |
| 결과 → 다시 하기 | 연습을 끝내고 새로 | 새 문장을 뽑는다 |

이어서 칠 수 있게 하니 확인 창이 필요 없어졌다. 다만 시간을 재는 방식 두 가지를
같이 고쳐야 했다.

### 연습 시간은 '재고 있는 구간들의 합' 으로 센다

시작 시각 하나만 두고 `지금 - 시작` 으로 빼면, 기록 화면에 1분 머문 시간까지
연습 시간에 들어간다. 그래서 멈출 때마다 그때까지 잰 만큼을 합에 더하고 구간을 닫는다.

```js
function currentElapsed() {
  return elapsedMs + (startedAt === null ? 0 : performance.now() - startedAt);
}
```

### 키 입력 시각도 벽시계가 아니라 경과 시간으로 잰다

처음에는 '돌아올 때 마지막 키의 시각을 지금으로 당기는' 보정 함수를 만들었다.
그런데 테스트가 바로 잡아냈다. 마지막 키의 시각을 바꾸면 **이미 확정된 그 키의
입력 시간까지 오염된다.** 150ms 였던 값이 30150ms 가 되어 버렸다.

보정하는 대신 기준 자체를 바꿨다. 키 입력 시각으로 벽시계 시각이 아니라
위에서 만든 `currentElapsed()` 를 넘긴다. 화면을 떠나 있는 동안은 시계가 멈춰
있으므로 그 시간이 애초에 더해지지 않고, 따로 보정할 일이 없어진다.
